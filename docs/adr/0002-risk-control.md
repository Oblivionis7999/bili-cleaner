# 风控策略：保守默认、单写入者、自动冷却与断点续跑

B 站对批量写操作（取关、删动态、取消收藏）没有官方批量接口，社区实测在数百次连续请求后会触发 `-352`（风控校验失败）、`-412`（IP 被拦截）、`-799`（请求过于频繁），甚至短信验证。因此工具默认：

- **单线程、单写入者**：同一时间只允许一个写任务执行，串行发请求。
- **保守节奏**：每条请求间隔 2.5 秒 ± 随机 0.8 秒；每批 20 条后休息 3 秒；连续 300 条后强制休息 10 分钟。
- **识别风控并冷却**：返回 `-352/-412/-509/-799` 时冷却 600 秒后重试同一批；连续两次冷却仍不通过则把任务置为 `stopped` 并提示"今天别继续了"。
- **断点续跑**：每个对象删成功/失败都写一行 JSONL；进程重启后从日志恢复，跳过已成功的对象。
- **不提供绕风控手段**：不改 UA 伪装、不并发冲刺、不做代理池。工具的目标是"慢一点但稳定、可预期"。

考虑过并放弃：并发/短间隔的"快速模式"（更容易被封、失败率不可控）、浏览器插件式复用页面按钮（依赖 DOM，B 站前端一改就废）。代价是清 4000+ 条数据可能要跑一两个小时——这个时间成本是显式的，写在界面上。
